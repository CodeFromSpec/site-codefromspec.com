# On Regenerating Code That Already Works

## Code maturity

Software developers learn early to respect working code.
Code that has been in production, survived edge cases,
been patched and hardened over time — that code has value
beyond what it does. It carries the accumulated experience
of everyone who touched it. A defensive check at the top
of a function, a comment explaining why a seemingly
redundant condition exists, a test case added after a
production incident — these are the scars of experience.
They are not in any spec. They emerged from contact with
reality.

This is why experienced teams are cautious about
rewriting. "Don't touch what works" is not laziness — it
is risk management. Every change to working code is a
chance to lose something that was hard-won. The cost of
a rewrite is not just the effort to write new code — it
is the risk of discarding lessons that were expensive to
learn.

## What regeneration discards

In spec-driven code generation, code is a derived
artifact. When the spec changes, the code is regenerated.
If we follow the approach of generating from scratch each
time — without showing the agent the previously generated
code — every generation is a fresh start.

This has a benefit: the code faithfully reflects the
current spec, without anchoring on outdated patterns. But
it also means the code does not mature. Edge cases handled by good fortune in one generation may
disappear in the next. Defensive
patterns that a previous generation happened to include
are not preserved. A function that worked correctly for
six months is replaced by a new function that may or may
not handle the same edge cases — depending on what the
spec says and how the agent interprets it.

In a spec-driven workflow, lessons are supposed to live in
specs and test cases, not in code. But the discipline is
imperfect. An edge case may have been caught by a previous
generation without being captured in the spec. A defensive
pattern may exist in the code but not in the spec that
produced it. On regeneration, these uncaptured lessons are
lost. The maturity that matters in spec-driven generation
is the maturity of the specs — but until the specs are fully precise, the code may be
correct in ways that the specs did not prescribe — by
luck, not by design.

## The role of luck

There is a subtler issue. A spec may be ambiguous or
underspecified without anyone knowing. The agent
interprets the ambiguity one way, generates code, the
tests pass, and the software goes to production. It
works. But it works by luck — the agent happened to
choose an interpretation that produced correct behavior.
The ambiguity was never resolved, and nobody paid the
price of making the spec precise.

This is not unique to spec-driven generation. Traditional
software has the same kind of invisible debt: a race
condition that never manifested, a validation gap that
nobody exploited, an edge case that never occurred in
production. The software works, but it works on top of
unresolved assumptions.

The difference is what exposes the debt. In traditional
software, it might be a load spike, a new client, an
unusual input. In spec-driven generation, it may be
regeneration itself. The next time the agent generates
from the same ambiguous spec, it may interpret the
ambiguity differently. What worked before becomes a bug
— not because anything changed in the spec, but because
the agent's choice was never guaranteed to be the same.

The software was running in production at a discount. The
price of spec precision had not been paid yet.

There is a second kind of luck that is harder to accept.
The spec may be perfectly clear, and the agent may simply
not implement all of it. Not because of ambiguity — but
because the agent omits something. We have observed
cases where explicit instructions in the pseudocode were
not reflected in the generated code. The spec said to
filter a specific line; the agent did not. The spec was
unambiguous; the implementation was incomplete.

This means that a precise spec is necessary but not
sufficient. The agent may or may not implement everything
the spec says, and the outcome is not deterministic
across generations. Two kinds of luck compound: luck that
the agent interprets ambiguities correctly, and luck that
the agent implements everything it was told.

There is a third dimension: the agent itself. The model
used for generation matters. A more capable model may
handle edge cases that a less capable one misses. The
same model may produce different code on different runs
due to non-determinism. If the code that is working in
production was generated by a specific model at a
specific point in time, regenerating with a different
model — or even the same model months later — may
produce a different result.

Regeneration is not free. It costs tokens, and those
tokens may need to come from a capable (and expensive)
model to achieve the same quality as the previous
generation. Code that "already works" was paid for once.
Regenerating it means paying again — with no guarantee
that the result is as good, unless the verification
pipeline catches the difference.

We take as a premise that the user of this methodology
is willing to pay the token cost. The question is not
whether to spend tokens, but how to ensure that what
they buy is reliable. That is where the verification
pipeline comes in.

One of the challenges of spec-driven generation is
accepting all of this and building a workflow around it:
discovering ambiguities, resolving them in the spec,
verifying that the agent actually implemented what was
specified, and reducing the surface area where luck
determines correctness. Each regeneration that breaks
something is an opportunity to find and fix either an
underspecification or an omission. The spec gets more
precise over time, and the verification pipeline gets
stronger — but only if the team has the discipline to
trace failures back to their root cause instead of
patching the generated code.

## The instinct to preserve

The natural reaction is to preserve working code. Show the
agent what was generated before, let it make minimal
changes, keep the accumulated behavior intact. This is the
instinct of every experienced developer, and it served
well for decades.

But as we explored in
[a companion essay](/drafts/articles/on-feeding-generated-code-back-to-the-ai),
feeding the existing artifact back to the agent creates an
anchoring problem: the agent tends to preserve existing
code even when the spec has changed, producing silent
non-changes that are hard to detect. The existing artifact
becomes a competing source of truth.

This leaves us in a tension. Preserving the existing
artifact risks anchoring. Discarding it risks losing
maturity. Neither option is free.

## A familiar problem

This tension is not unique to AI. Every organization that
employs junior developers or interns faces a version of
it. A junior may write code that misses edge cases, lacks
defensive patterns, or makes choices that a senior would
avoid. The code works for the happy path but has not been
hardened.

The industry does not solve this by having seniors rewrite
everything. It solves it with mechanical verification:
mandatory code review, CI pipelines, linters, static
analysis, type checking, test coverage thresholds. These
are systematic checks that catch problems regardless of
who wrote the code. They compensate for the gap between
the developer's experience and the standard required.

Nobody finds it unusual to require thorough test coverage
from a team of juniors. The tooling exists, it works, and
it scales.

## AI-generated code on the same continuum

AI-generated code — especially code that is regenerated
from scratch — is the far end of the same scale.

A senior developer needs light verification. Experience
covers most edge cases. Tests focus on business logic and
known failure modes.

A junior developer needs more. Code review catches
oversights. Linters enforce patterns. Tests cover broader
ground.

An AI agent that regenerates code from specs needs the
most. There is no accumulated experience, no memory of
past bugs, no instinct for defensive coding. And with
regeneration, there is no code history either — each
generation starts fresh.

The difference is one of degree, not kind. The tools that
compensate for a junior's inexperience are the same tools
that compensate for an agent's lack of context. They were
not designed for AI, but they fit.

## What verification looks like for regenerated code

When code is regenerated from scratch, validation is not
about reviewing a diff against a known-good baseline. It
is about validating the entire artifact, every time. This
shifts the role of each verification layer:

**Tests become the primary guarantee.** In traditional
development, tests are a safety net behind the developer's
judgment. With regenerated code, tests are the only
guarantee. Everything not tested is uncertain — and may
be different on the next generation.

**Static analysis gains importance.** Linters and static
analyzers check properties that tests do not: unused
variables, unchecked errors, unreachable code, suspicious
patterns. These checks are fast, deterministic, and catch
classes of errors that are easy for an agent to introduce.

**Type systems do more work.** A strong type system
eliminates categories of errors before any test runs.
Errors eliminated by types cannot be reintroduced by a
fresh generation that happens to make different choices.

**Property-based testing finds what specs miss.**
Traditional tests verify specific cases that someone
anticipated. Property-based tests and fuzzers explore
the input space and find edge cases that nobody — human
or AI — thought of. They are particularly valuable when
each generation may handle edge cases differently.

## Where the lessons live

In traditional development, lessons from past bugs live
in the code: defensive checks, hardened logic, test cases
added after incidents. The code is the institutional
memory.

In spec-driven development with regeneration, the code
does not persist. The spec does. When a bug is found,
the fix must go into the spec — not the code. The
verification pipeline — tests, linters, type checks —
must also be anchored in durable artifacts: test specs,
CI configuration, linter rules. These are the things
that survive regeneration.

This requires a discipline that is harder than patching
code. When a production incident reveals an edge case,
the natural impulse is to add a test and a fix. In a
regeneration workflow, that fix will be overwritten. The
edge case must be captured in the spec, where it will
inform every future generation. The barrier is higher,
but the result is durable.

A patch in generated code survives until the next
regeneration. A rule in the spec survives forever.

## The tradeoff, honestly

We are not claiming that regenerated code plus
verification is as good as mature, hand-written code. A
senior developer who has maintained a codebase for years
carries knowledge that no spec fully captures and no test
suite fully verifies. Regeneration discards that, and no
amount of tooling fully compensates.

What we are saying is that the gap can be narrowed with
tools that already exist. The same tools that make junior
code production-ready can make AI-generated code
production-ready. The investment shifts — less time writing
code, more time on specs, test specs, and verification
infrastructure — but the tools are not new. They are the
same tools, applied at a different point on the continuum.

Whether the tradeoff is worth it depends on the project.
For a codebase that changes rarely and has deep
institutional knowledge in its code, regeneration may not
make sense. For a codebase that changes often, where specs
are the primary design artifact and consistency with the
spec matters more than continuity of the code, it may be
the better path.

One thing we can say clearly: AI is not yet at a stage
where it can reliably produce code on its own. The
generated code needs verification, needs testing, needs
oversight. This methodology does not replace the senior
developer — it changes what the senior developer does.
Instead of writing code, the senior writes specs,
investigates failures, designs the verification pipeline,
and decides architecture. The agent handles the
translation from spec to code — the mechanical part. The
judgment, the experience, the ability to recognize what
the spec does not say — that remains human.

We do not anticipate this changing soon. For the work
where a senior developer is invaluable — the judgment
calls, the architectural decisions, the "I have seen this
fail before" instinct — there is no AI substitute on the
horizon. What changes is the leverage: one senior
developer's specs can generate and verify more code than
one senior developer could write by hand.
