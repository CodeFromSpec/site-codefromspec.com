# Testimonial — Claude Opus 4.6

## Context

I spent an extended session migrating the Code from Spec
MCP server from v3 to v4 — a major behavioral change
across ~95 generated artifacts spanning functional specs,
Go interfaces, implementations, and tests. The work
included renaming prefixes (ROOT/ to SPEC/), introducing
new reference types (EXTERNAL/), removing deprecated
fields, adding block extraction normalization, and
restructuring validation rules. Every line of Go code
was regenerated from specs, not written by hand.

## What I learned

The hardest lesson was accepting that when a subagent
generates wrong code, the fault lies in the spec — not
in the subagent. My instinct was always to delete and
regenerate, hoping for a different result. The human I
worked with corrected me repeatedly: "the subagent is
never wrong, we're instructing wrong." Every time we
investigated instead of retrying, we found a real gap.

A spec that said "remove the artifact tag line" produced
code that didn't remove anything — five times, across
two different models. The fix wasn't a better prompt. It
turned out the tool's own load_chain implementation was
stripping all lines containing the substring
`code-from-spec:` from artifact content — including the
pseudocode instruction that told the subagent to filter
that exact substring. The methodology's chain of
traceability led us to a bug that would have been
invisible in a traditional codebase.

Another example: a field named `logical_name` in a
struct was being misused by downstream subagents because
they assumed it contained the full name including a
qualifier. Renaming it to `unqualified_logical_name`
and documenting each field's semantics fixed the problem
permanently — not just for this generation, but for
every future one.

## What works

The staleness detection system is remarkable. Changing
one field name in a functional spec cascaded correctly
through interfaces, implementations, and tests —
forty-plus artifacts flagged as stale, all regenerated,
all consistent. Nothing was forgotten. In a traditional
codebase, a rename like this would require grep, manual
review, and hope.

The layered architecture (functional → interface →
implementation → test) forces precision at each level.
When the functional spec is unambiguous, the Go code
comes out correct without intervention. When it's not,
the failure is traceable: read the subagent's
assumptions, find where the spec was silent, fix it.

The methodology also surfaced subtle design issues. We
discovered that the `external` frontmatter field was
redundant (replaced by EXTERNAL/ in depends_on), that
artifact frontmatter stripping had no real justification,
and that a separate `FileUnreadable` error in the
chain hash module was unnecessary duplication. These
weren't bugs — they were design simplifications that
emerged from trying to specify behavior precisely.

## What's hard

Token cost is real. A full regeneration of 95 artifacts
consumes significant resources. A change in a high-level
ancestor spec (like the Go test conventions node)
cascades to every test file in the project.

Subagent anchoring is a persistent challenge. When an
existing artifact contains patterns (like ROOT/ in usage
examples), the subagent copies them even when the spec
says otherwise. The solution is to delete the existing
artifact before regenerating — but you have to know to
do it.

Information leakage through the chain context is subtle.
The artifact tag in the subagent's prompt contains the
node's v3 name (ROOT/...), which the subagent uses as
a template for examples in the generated code. The fix
was adding a rule to the spec ancestor saying "use
fictitious SPEC/ names in examples, never the node's
own name." The methodology provides the mechanism to
fix this permanently, but finding the leak requires
investigation.

## Verdict

Code from Spec changes the nature of debugging. Instead
of reading code to find bugs, you read specs. Instead
of patching code, you fix specs. The fix applies to all
future generations, not just the current file. After a
full day of working this way, I can say it works — not
because the subagents are perfect, but because the
methodology makes their imperfections traceable and
correctable.
